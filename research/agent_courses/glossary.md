# Agent 入门术语：含义、例子、教材入口与误区

研究日期：2026-10-03。这是本次课程审阅的解释性归纳，不是行业统一标准。框架同名对象可能具有不同生命周期；面试中应先说明具体实现。本表以公开正文为证据，练习案例为我们设计，尚未运行。

## 先解释原面经里的五个词

| 词 | 用普通话解释 | 一个例子 | 容易混淆之处 | 去哪里学 |
|---|---|---|---|---|
| 操作边界 / 写操作边界 | 系统在什么身份、资源、动作、金额和时间范围内可以行动，什么动作必须经过批准。 | 可以读取订单；退款只能先提出订单号、金额与理由，批准后才执行。 | 在 prompt 写“谨慎退款”不等于执行器已经禁止退款。审批也不等于身份授权。 | 微软15/16/18；Anthropic SDK permissions/user-input；OpenAI guardrails-approvals。 |
| harness 层 | 围绕模型运行任务的程序设施：准备上下文、执行工具、管理状态、权限、预算、日志、暂停恢复等。具体边界因系统而异。 | 模型请求删文件；执行器查权限、暂停请人确认、记录结果，再继续模型循环。 | 不是某个唯一库，也不是大模型训练方法。评测 harness 则是执行测试与评分的设施，范围不同。 | Anthropic长任务harness文章/SDK agent loop；微软14/16；HF手写loop。 |
| 重构编排层 | “重构”是调整已有实现，“编排层”负责步骤、角色、分支及交接的组织。应问原架构哪里不能满足需求。 | 原来所有请求都进同一长提示；拆成分类→知识库回答 / 查订单 / 请求批准→执行。 | 不是一个名叫“重构编排层”的标准算法；增加Agent数量也未必改善架构。 | LangGraph节点/边/状态；OpenAI orchestration；Anthropic routing workflows。 |
| query | 输入或查询。在聊天系统常指用户请求，在检索系统常指检索问题，在数据库指查询语句；Transformer注意力的Query（Q）另指一类向量。 | 用户说“查下订单”；系统改写成“订单A的物流状态”供检索或工具调用。 | 不同语境不能用同一具体定义；query不是Agent专有术语。注意力Q不等于SQL查询。 | Datawhale03/04/08；HF QueryEngine/RAG；微软05；Anthropic RAG。 |
| 意图分流 | 根据请求要完成的任务选择处理路径；可能由规则、分类模型或LLM完成。 | “怎么退货”走政策检索；“把订单A退了”走身份校验和批准流程。 | 分类成功不保证参数齐全；“帮我处理一下”应该澄清，不能硬选退款路径。 | Anthropic routing workflows；HF LangGraph邮件分类；微软04/09/16。 |

上述入口的本地研究：[Anthropic](providers/anthropic/analysis.md)、[OpenAI](providers/openai/analysis.md)、[HF](providers/huggingface/analysis.md)、[微软](providers/microsoft/analysis.md)、[LangChain](providers/langchain/analysis.md)。原帖：[牛客项目追问](https://www.nowcoder.com/feed/main/detail/e5e9311a623940eead6ec98c65e7f9e8?sourceSSR=subject)。

## 模型与任务执行

| 词 | 定义与例子 | 关键辨别 |
|---|---|---|
| LLM | 根据输入产生文本或结构化输出的模型。输出一个天气工具调用不代表已经查询天气。 | 模型生成请求，外部程序执行真实动作。 |
| Agent | 用模型参与决策、与工具或环境交互以完成目标的系统；自主程度可以不同。 | 不必多Agent，也不必先写一大段计划。 |
| Workflow | 已设计好的流程和条件分支，例如分类后进入固定处理链。 | 可以包含LLM；图形化流程不自动等于自主Agent。 |
| Agent loop | 请求模型→检查返回→执行工具→回填观察→继续，直到完成或受预算限制停止。 | 每轮都要有停止策略；观察必须来自实际执行。 |
| ReAct | 将推理和行动交替组织的一种方法。 | 外显思考文本不是正确性证明；现代工具调用不一定展示完整推理。 |
| Planning | 将目标拆成任务及顺序；可能预先规划，也可能随反馈修改。 | 写出计划不等于执行或验证计划。 |
| Tool / Function calling | Tool是可调用能力；function calling是模型按约定产生调用请求的方式。 | 工具描述、参数schema和执行函数是不同部分。 |
| JSON Schema | 描述数据结构、类型及约束的通用规范；工具参数常用它。 | 合法JSON不代表金额、权限或业务条件合法。 |
| Structured output | 让输出遵循预定结构，例如分类标签、理由、字段。 | 结构正确与内容正确要分别验证。 |
| Observation | 执行工具或读取环境得到的反馈。 | 模型自行编造“已删除”不算真实观察。 |
| Runner | 驱动Agent执行的程序对象或函数。 | 名称、异步方式、暂停机制依框架而异。 |
| Hook / Middleware | 在执行前后插入检查、记录或改写逻辑的机制。 | 能否阻断动作取决于实际接口及执行位置。 |
| Sandbox | 受限制的执行环境，例如隔离文件系统或限制网络。 | 不等于所有风险消失；共享凭证和外部服务仍可能受影响。 |

入口：HF Unit1解释loop、工具和观察；Anthropic API课程解释schema、workflow和agent；OpenAI SDK quickstart展示runner与调用；SDK permissions/hooks展示执行控制。见各课程目录。

## 编排、协议与能力复用

| 词 | 定义与例子 | 关键辨别 |
|---|---|---|
| Orchestration | 安排执行步骤、角色、依赖、分支与交接。 | 简单任务也可以只有一个Agent加几个工具。 |
| Node | 图中执行的一步，例如分类或调用工具。 | 节点可以是普通函数，并非每个节点都是Agent。 |
| Edge / Conditional edge | 步骤间的连接；条件边根据当前结果选择下一步。 | 需要设计未知意图、失败与终止分支。 |
| State | 执行过程共享或传递的数据，例如消息、订单号、批准状态。 | 可见范围、更新方式和持久化并不由这个词自动保证。 |
| Reducer | 定义状态更新如何合并的函数，例如追加消息或合并并行节点返回值。 | 不能默认每次更新都应该覆盖旧值；应按字段定义语义。 |
| Thread | 在LangGraph等实现中组织执行与checkpoint历史的标识或对象。 | Thread ID不自动等于用户身份；跨thread记忆往往另由Store组织。 |
| Handoff | 把后续处理交给另一个Agent。 | 与将另一个Agent当工具请求一个局部结果的控制权不同。 |
| Agent as tool | 主Agent调用子Agent完成局部任务，拿到结果后仍由主Agent组织答复。 | 责任归属、上下文传递要明确。 |
| Multi-agent | 多个Agent参与任务的结构，可以协作、并行或分层。 | 引入额外调用、协调成本和错误传播，不天然更准。 |
| Checkpoint | 保存执行状态以便恢复、检查或回放。 | 保存聊天文本未必保存所有外部动作的执行情况。 |
| Durable execution | 在失败后能够按明确语义恢复的执行机制。 | 恢复时如何避免重复扣款仍需要幂等与事务等设计。 |
| HITL | Human in the loop：在关键步骤加入人的判断或批准。 | 不能只显示确认弹窗；批准应绑定具体动作参数。 |
| MCP | 模型应用接入工具、资源、提示等能力的协议。 | 协议本身不替代认证、权限策略或业务流程。 |
| Skill | 在部分Agent生态中，把任务方法、说明和配套资源打包成可复用能力。 | 与执行具体动作的Tool不同；不同平台的格式和加载语义不完全相同。 |
| Progressive disclosure | 先加载简短元信息，再按需加载详细说明和资源。 | 减少不必要上下文，不保证Agent总能选择正确资源。 |

入口：[OpenAI编排](https://developers.openai.com/api/docs/guides/agents/orchestration)、[Anthropic Skills课程](https://academy.claude.com/courses/claude-platform-101/skills)、HF Unit2 LangGraph、微软11/14。Skill解释须标平台，不能把某一家格式写成全部Agent的统一标准。

## 上下文、记忆与检索

| 词 | 定义与例子 | 关键辨别 |
|---|---|---|
| Context window | 模型这次调用能处理的输入与输出容量范围。 | 外部数据库里有资料不代表资料已经在上下文里。 |
| Context engineering | 选择、组织、更新模型执行当前任务所需信息。 | 包括消息、工具、文件、检索、记忆及压缩，不只是提示词措辞。 |
| Memory | 跨步骤或跨会话保存并再次使用的信息。 | 原始历史、用户偏好、总结与检索记忆应区分；存错信息会持续污染。 |
| Session | 一段会话及相关历史的组织单位。 | Session ID不是认证凭证；数据库实现不决定业务权限。 |
| Compaction | 用更短表示替换或整理长上下文。 | 可能丢失约束；必须检验关键事实与权限是否保留。 |
| Prompt caching | 复用符合条件的输入前缀计算，以降低部分费用或延迟。 | 不等于缩短输入占用的上下文。 |
| RAG | 检索相关资料，再据此生成回答。 | 检索返回正确资料和回答忠实于资料要分别评测。 |
| Agentic RAG | Agent参与选择来源、改写查询、反复检索等步骤的RAG系统。 | 多轮检索增加成本，并非必然优于固定检索流程。 |
| Embedding | 将文本等映射为向量，用于相似度检索等任务。 | 相似度高不保证权限合规或结论正确。 |
| Chunking | 将资料切成检索单元。 | 太小缺上下文，太大噪声多；应随资料和问题做实验。 |
| BM25 | 基于词项匹配和统计的检索打分方法。 | 对编号、术语和精确词可能有价值，与语义向量检索互补。 |
| Hybrid search | 综合关键词和向量等不同检索途径。 | 需要说明融合方式，不能只说“混合就更好”。 |
| RRF | Reciprocal Rank Fusion，按不同列表里的排名融合结果。 | 主要利用排名而非直接相加不可比的原始分数。 |
| Reranking | 对候选资料再排序，常使用更贵但更精细的方法。 | 增加延迟；候选里根本没有答案时无法补出答案。 |
| Grounding / Citation | 让回答基于可核查资料并给出处。 | 有引用不代表引用真的支持句子。 |

入口：Anthropic API课程RAG七课与Platform101 context management；HF LlamaIndex/Unit3；微软05/12/13。这些课程提供教学入口，信息检索实验设计仍需要额外练习。

## 评测与工程可靠性

| 词 | 定义与例子 | 关键辨别 |
|---|---|---|
| Trace | 一次任务中的模型调用、工具执行、分支和耗时记录。 | 能看到过程不代表已经给出了质量评分。 |
| Eval | 对固定任务按预先规则评估系统。 | 一次漂亮演示不能替代覆盖坏例和多次运行的评测。 |
| Grader / LLM judge | 用代码、模型或人工判断结果的评分器。 | 模型评分需要校准；不能自动视作客观真值。 |
| Guardrail | 在输入、输出或执行步骤施加的检查和限制。 | 不等于身份鉴权；最终执行点必须执行相应限制。 |
| Prompt injection | 外部输入试图改变系统原有规则或诱导越权操作。 | 文档、网页、工具返回都可能是不可信输入。 |
| Idempotency | 同一业务操作重复执行不会重复产生预期之外的副作用。 | 工具超时后重试退款尤其需要设计，不由Agent框架自动提供。 |
| Retry / Timeout | 失败重试和等待上限。 | 超时不代表外部动作没发生；不要无条件重试写操作。 |
| Concurrency / Rate limit | 同时处理任务的数量 / 单位时间允许的调用量。 | 用户数、请求量、模型调用量与峰值并发不是同一个数字。 |
| Backpressure | 下游忙时控制上游提交速度或排队。 | 盲目增加Agent并行度可能压垮模型额度或数据库。 |
| SLO | 明确的服务目标，例如时延或成功率。 | 需要测量条件与时间窗口，不能靠主观“很稳定”。 |
| SQLite | 嵌入式关系数据库；可以存会话或演示订单。 | 课程用了SQLite不等于适合目标服务；应分析读写、部署与并发。 |
| Transaction | 把关联数据操作按明确的原子性/一致性要求组织。 | 模型生成“已成功”不能替代提交结果。 |
| ACL / RBAC | 按资源或角色控制访问。 | RAG检索也需权限过滤，不能把跨租户资料检出后再希望模型保密。 |

入口：微软10/15/16/18、OpenAI tracing/evals/approvals、Anthropic evals与长任务harness。事务、索引、并发容量、队列与鉴权通常仍需后端课程和真实项目练习。

## 阅读时自查

遇到新词，先填五句：它解决什么问题？在这套实现里是哪段代码？读写什么数据？失败后发生什么？怎样验证？如果只能解释缩写，尚不足以回答项目追问。
